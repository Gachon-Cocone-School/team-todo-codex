# 성능 감사 보고서

- 감사일: 2026-10-07
- 대상: 단일 Uvicorn 프로세스의 FastAPI API와 파일 기반 SQLite
- 실행 환경: Python 3.11.6, 로컬 개발 머신, loopback HTTP, 임시 SQLite DB
- 판정: **150개 동시 생성 burst에서 오류 없이 처리. 큰 읽기 burst는 성공하지만 대기 지연이 높음.**

## 요약

초기 측정에서는 SQLAlchemy 기본 `QueuePool` 제한에 도달해 풀 대기 timeout이 발생했고, 공통 태그 동시 생성에서 `409` 충돌도 관측됐다. 개선 후 요청 동시 실행을 풀 최대 크기(`pool_size + max_overflow`, 기본 30)에 제한하고, SQLite 쓰기 트랜잭션을 프로세스 안에서 직렬화했다. 태그는 먼저 조회하고 없는 경우 SQLite 원자적 upsert로 생성한다. SQLite 파일 DB에는 WAL과 busy timeout을 적용한다.

개선 후 같은 태그를 사용하는 150개 동시 `POST`가 모두 성공했다. 읽기 전용 750개 요청도 모두 성공했지만, 150개 클라이언트가 한 번에 몰리는 조건에서 p95가 11.6초로 높았다. 강한 burst에서 요청 대기 시간이 성능 한계로 남는다.

## 측정 결과

### 쓰기 burst

각 요청은 Todo 한 건을 생성하며 공통 태그를 사용했다. 각 동시성 단계는 별도의 동시 요청 묶음이다.

| 시점 | 동시 요청 | 결과 | 경과 시간 | 처리량 | p50 | p95 | p99 |
|---|---:|---|---:|---:|---:|---:|---:|
| 개선 전 | 50 | 200개 CRUD 작업 중 POST 192 성공, 8건 `409` | 3.58초 | 약 163 작업/초 | 0.699초 | 0.945초 | 0.988초 |
| 개선 전 | 150 | QueuePool 한도 초과 및 30초 커넥션 대기 오류 관측 | 완료 전 중단 | — | — | — | — |
| 개선 후 | 50 | POST 50/50 성공 | 0.12초 | 약 417 생성/초 | 0.070초 | 0.097초 | 0.099초 |
| 개선 후 | 150 | POST 150/150 성공 | 0.51초 | 약 295 생성/초 | 0.203초 | 0.437초 | 0.462초 |

개선 전 결과는 오류 원인을 확인하기 위해 사용한 초기 부하 실행이다. 개선 후 결과는 동일한 로컬 머신의 임시 파일 DB에서 얻었으며, 하드웨어·디스크·OS별 성능 보증으로 해석하면 안 된다.

### 읽기 burst

150개 클라이언트에서 총 750개 요청을 동시에 보냈다. 요청 절반은 `limit=100` 목록 및 태그 필터 조회, 나머지는 단건 조회였다. DB에는 약 200건이 있었다.

| 요청 수 | 성공 | 경과 시간 | 처리량 | p50 | p95 | p99 |
|---:|---:|---:|---:|---:|---:|---:|
| 750 | 750 (`200 OK`) | 12.59초 | 약 59.6 요청/초 | 8.150초 | 11.595초 | 12.199초 |

이 값은 요청 150개씩이 아니라 750개를 한 번에 몰아넣은 포화 burst의 응답 지연이다. 측정 결과만으로 개별 SQL이나 JSON 직렬화가 지연의 어느 비율을 차지하는지 분리하지는 못했다. 요청 제한 대기와 작은 로컬 SQLite 부하가 함께 반영돼 있다.

## 현재 구현의 성능 특성

- 최대 100건 페이지 상한과 `selectin` 태그 로딩으로 목록 응답의 태그 조회가 항목별 N+1 질의가 되지 않도록 했다.
- 쓰기 트랜잭션은 SQLite 단일 writer 특성에 맞춰 앱 프로세스 안에서 하나씩 실행한다. 이로써 동시 writer 경합이 풀 고갈로 번지는 것을 막지만, 쓰기 처리량은 직렬 실행에 제한된다.
- 요청 admission semaphore는 풀 최대 크기와 맞춘다. 초과 요청은 DB 진입 전에 대기한다. 폭주 상황의 커넥션 timeout을 줄이는 대신 tail latency가 커질 수 있다.
- 기본 정렬(`created_at DESC, id DESC`)에 맞춘 복합 인덱스는 없다. 데이터가 커지면 정렬 비용을 실제 쿼리 계획과 함께 측정하고, 필요하면 인덱스를 추가한다.
- SQLite 직렬화 락은 단일 프로세스 안에서만 동작한다. 여러 Uvicorn worker나 여러 앱 인스턴스에서 SQLite 파일을 동시에 쓰는 운영은 이 감사에서 검증하지 않았다.

## 권고

1. 요청률과 p95/p99를 운영 기준으로 정하고, 목록 조회를 더 큰 데이터셋(예: 10만 Todo, 태그 분포 포함)에서 반복 측정한다.
2. 읽기 burst의 대기 지연이 기준을 넘으면 목록 질의 계획, 응답 크기/직렬화 비용을 프로파일링하고 요청 한도와 풀 크기를 함께 조정한다.
3. 쓰기 부하가 늘거나 다중 프로세스 운영이 필요해지면 SQLite를 여러 worker로 공유하지 말고 PostgreSQL 같은 동시 쓰기 DB로 전환한다.
4. 대량 목록이 일반적이면 offset 기반 페이지네이션 대신 cursor 기반 페이지네이션을 검토한다.

## 검증 명령과 한계

- `uv run pytest tests/test_todos.py -q`: 14개 통과
- `./scripts/check.sh`: Ruff lint, 포맷 확인, pytest 전체 통과
- HTTP 부하는 Uvicorn 단일 프로세스와 로컬 임시 SQLite DB에서 `httpx.AsyncClient`로 실행했다. 외부 네트워크, 다중 worker, 장시간 soak, 혼합 운영 트래픽, CPU·메모리 프로파일링은 포함하지 않았다.
